## Blocking finding

### QA-0004-003 — extra own Symbol scope key bypasses exact-shape authorization validation

- Severity: High; acceptance-blocking security defect.
- Root cause: `normalizeScope` uses `Object.getOwnPropertyDescriptors(value)` and then `Object.keys(descriptors)`. `Object.keys` excludes symbol keys, so a fourth attacker-controlled own symbol property is invisible to the exact-shape comparison.
- Exact reproduction: instantiate `RawEvidenceIntakeService` with `deriveScope` returning `{ ...validScope, [Symbol("hidden")]: "attacker-controlled" }`; instrument the scanner; submit an otherwise valid synthetic intake request; assert the standard `403 forbidden` denial.
- Observed at exact candidate: assertion failed. The service returned `201`, `scannerCalls` was `1`, and `audit().length` was `1` with a quarantined record. The response did not disclose the symbol value, but the malformed authorization adapter shape was accepted and mutated state.
- Expected: identical bounded `403 forbidden` denial before scanner, record, idempotency, or audit mutation, followed by a successful corrected retry using the same idempotency key after the adapter returns the exact three-field scope.
- Required remediation: in a separate Backend corrective-forward commit, validate the complete own-key set including string and symbol keys (for example, a fail-closed `Reflect.ownKeys`-equivalent check under the existing trap boundary), retain descriptor-based no-getter/no-coercion handling, and add intake/get negatives for extra symbol keys plus no-scanner/no-state/no-audit and corrected-retry assertions. Do not weaken exact-shape semantics or erase the R1/R2 rejection chain.
